# 我用 Rust 写了一个「去中心化」的文学站点，顺便把运维也省了

我有个写东西的朋友，她把文稿放在某个写作平台上。上个月平台改了规则，她的十几万字一夜之间变成"仅自己可见"——理由是"内容不符合社区规范"，但具体哪里不符合，客服只说"请自行检查"。

她去申诉，三天后回复：**根据算法检测，您的文章疑似存在低质量内容。**

十几万字，一个算法判了死刑。

我跟她说："你把文稿给我，我帮你搭个网站。"

她说："我不会写代码。"

我说："你不需要会。"

这就是我写 **soil** 的起因。

---

## 一、怎么让一个不会 Git 的人，把文章发布到 GitHub Pages 上？

答案很简单：**让工具替她操作 Git，她只需要点几下键盘就行。**

soil 是一个 Rust 写的单二进制 CLI 工具，安装只需要一行命令（Windows/macOS/Linux 都有安装脚本）。作者在自己的文稿目录下运行：

```sh
soil submit
```

然后按提示操作即可。背后发生了什么？

1. **OAuth 登录 GitHub**（设备授权流，浏览器扫一次码，之后自动记住 token）
2. **自动初始化/复用文稿仓库**——如果这个目录还不是 git 仓库，soil 帮你 `git init`、`git remote add`、`git push`；如果已经是，直接复用
3. **把作者的仓库作为 submodule 挂到本站仓库下**——提交一条 PR（Pull Request）到主站仓库，内容是 `authors/<作者名>` 这个子模块的 url + commit hash
4. **本地预览**——soil 内嵌了一个静态站点生成器（sitegen），拉取当前所有作者的文稿，本地构建一遍网站并在浏览器里打开，让作者立刻看到效果

整个流程，作者全程面对的是"输入路径→输入名称→看预览"这种对话式的交互。她甚至不太需要理解 git 是什么、submodule 是什么、PR 是什么。

而支撑这套流程的底层架构，才是我想聊的重点。

---

## 二、为什么用 Git Submodule 而不是数据库？

这是我做这个项目最得意的设计决策：**不用数据库，不用后端，不用 CMS。整个站点是一个纯粹的静态 HTML 目录。**

核心架构只有三样东西：

| 组件 | 角色 |
|------|------|
| **Git Submodule** | 内容分发层。每个作者维护自己的独立仓库，本站只记录一条指向"ta 仓库的某个 commit"的链接 |
| **sitegen** | 静态站点生成器。用 Rust 写，基于 pulldown-cmark 解析 markdown，用 `format!` 拼 HTML（没引入模板引擎，图省事） |
| **GitHub Pages + Actions** | 托管 + CI/CD。每次 push 触发构建，`dist/` 目录上传到 Pages，全球 CDN 分发 |

为什么用 submodule 而不是直接把作者的文件放到 `authors/` 目录下？

因为 **submodule 本质上是一个指针，不是副本**。

这意味着：
- **作者永远拥有自己的数据**——文稿放在自己名下仓库里，随时可以删、改、设为私有、迁移到其他平台。本站没有"保管"任何人的文件，只有一条指向历史的引用
- **本站下架 ≠ 内容消失**——即使主站仓库被删了，作者的仓库完好无损。反过来，作者退出只需要删掉 `.gitmodules` 里的一行
- **天然版本历史**——每条 submodule 记录的 commit hash 就是一次"快照"。站点构建的时候 checkout 到哪个 commit，登出来的就是哪个版本的内容

这种设计规避了绝大多数内容平台的"数据绑架"问题：平台关了，你的东西就没了。但在开源文艺里，即便这个站点明天消失，任何有 Fork 的人都可以用 `cargo run -- --out-dir dist` 一行命令重新把全站构建出来。

而"凭什么你能用别人的内容重建站点"——因为它是 **GitHub Pages**，所有内容本来就是公开的。公开不是缺陷，是设计目标。

## 三、CI/CD 的自动化链路

部署流程也很"懒"——全部扔给 GitHub Actions，我没管过第二次。

```
作者更新自己的仓库（commit + push）
        │
        │  不直接触发任何事
        │
        ▼（每天 UTC 3:57 定时）
[Auto Update Submodules Workflow]
  git submodule update --remote   ← 拉取所有作者的最新 commit
  git diff → 有变更 → commit + push
        │
        ▼
[Deploy Workflow]
  checkout submodules: recursive
  cargo test --release
  cargo run -- --out-dir dist --check-links  ← 断链检测
  upload dist/ → GitHub Pages
```

两个关键设计：

1. **作者更新自己的仓库不会立刻触发构建**。只有上游仓库的 submodule gitlink 更新了，deploy workflow 才会跑。这是为了避免作者频繁 commit 时构建队列爆炸，同时**只构建"站点维护者确认过的内容版本"**（PR 机制保证了这一点）

2. **每日自动拉取所有已收录作者的最新内容**。也就是说，作者在 PR 被合并过一次之后，后续的更新**不再需要走审核流程**——soil 内部的 `AUTO_UPDATE_ENABLED` 常量控制这条线，日常开着，紧急需要立即上线的作者可以临时关掉，soil 就会创建一条更新型 PR

这个设计平衡了三个需求：
- 新作者内容有人审（PR）
- 已收录作者更新无需重复审（自动同步）
- 紧急情况可以绕过等待（关掉自动更新即可走手动 PR）

## 四、soil 的交互设计里几个有意思的细节

写 CLI 工具的人都知道，最难的不是实现功能，是**处理用户的"意外操作"**。soil 面对的是完全不懂终端的非程序员，我踩了不少坑：

- **Ctrl+C 在 Windows 终端里是复制快捷键**——如果按 Ctrl+C 就退出，用户复制一段文字整行都没了。所以 soil 用 `ctrlc` crate 吞掉了 `SIGINT`，改成 **Esc 才是退出键**

- **网络不稳？无限重试**——`git push` / `git clone` 等网络操作如果报 `connection reset` / `timeout` 等错误，soil 每 3 秒重试一次，不停，文案显示"第 N 次失败"。用户不用管，等网络恢复就自动继续。但认证失败、仓库不存在这种"不可能通过重试解决"的错误则立即报出

- **SSH 自动探测**——如果用户有 GitHub SSH key 且能成功认证，soil 自动配置 `url.git@github.com:.insteadOf https://github.com/`（仅本地 config，不提交到仓库）。Git LFS 用户都懂这种"自动切 SSH 通道"有多省心

- **Git 已经是仓库了怎么办？没有 origin 又怎么办？**——`step_manuscript` 函数按目录状态分三条支路处理：有 git + 有 origin → 复用；有 git + 无 origin → 问 URL；无 git → 初始化。逻辑不复杂但覆盖了所有组合

这些细节很"小"，但写工具的人会理解——一个面向非技术用户的 CLI 工具，**健壮性比功能列表更重要**。

## 五、技术栈一览

整个项目是一个 Cargo workspace，两个 crate：

- **sitegen**（根 crate）：`pulldown-cmark` 解析 markdown，`walkdir` 遍历 `authors/`，`format!` 生成 HTML，`rand` 给首页做随机推荐（纯客户端 JS 打乱，构建时不随机）。UTF-8 原生文件名、无 slug 化、BOM 自动剥离。
- **soil**：内嵌 sitegen 库，依赖 `dirs` 管理 token 缓存，用 GitHub REST API 做 OAuth 和 PR 操作。无第三方 HTTP 客户端，全部用 `ureq`（保持二进制体积小）。

构建产物：sitegen + sitegen lib + soil 单二进制。CI 矩阵编译 Windows / Linux / macOS（x86_64 + ARM64），每次代码变更自动发布到 `latest` release 标签。

**全部不到 2000 行 Rust，包含测试**。没有 Rust 信仰加成——只是这个场景确实很适合零成本抽象的静态类型语言。编译器帮我防住了不知道多少空指针和 UTF-8 编码错误。

## 六、最后

这个项目其实不算"技术含量高"，架构选型也都是现成的老东西：git submodule、GitHub Pages、静态站点生成、CI/CD。甚至可以说，十年前就能用 Jekyll 搭出一模一样的东西。

但十年过去了，中文互联网上依然没有一个让写作者"自己的数据自己管，自己的网站自己能构建"的方案——原因不在技术，而在商业模式：内容平台需要通过数据垄断来维持流量护城河。

开源文艺不解决任何商业问题。它甚至不追求用户量——它的设计假设就是"每个作者自己就能跑起来"。

如果你的朋友也在某个平台受够了算法之墙，告诉他们：**有一个办法让你的文字永远属于你自己，而且只需要一个 GitHub 账号。**

代码在 [github.com/windwhiterain/open-literature-and-art](https://github.com/windwhiterain/open-literature-and-art)，soil 下载页在 [Releases](https://github.com/windwhiterain/open-literature-and-art/releases)。
